一个博客最容易停留在“已经能打开”的阶段。

主题装好、域名能访问、首页有图，看起来就像完成了。但只要继续往下写，很快会遇到更具体的问题：旧示例文章还排在列表里，导航里有点不开的入口，关于页写的仍是模板介绍，部署地址变化后资源路径全部失效。

这些问题不会阻止第一次访问，却会阻止站点长期成长。

## 模板解决的是“起点”

Firefly 已经提供了足够完整的起点：Astro 路由、Svelte 交互组件、文章集合、标签与分类、系列页、搜索、RSS、响应式布局和多种视觉模式。

模板擅长回答“一个博客可以长什么样”，却不应该替站点回答下面几个问题：

- 这个站是谁的？
- 它主要记录什么？
- 哪些页面现在就有真实内容？
- 访客第一次进入时应该从哪里开始？
- 三个月后再加内容，会不会逐渐失控？

如果这些问题没有答案，功能越多，维护成本反而越高。

## 先分清四层工作

这次整理把站点拆成四层，而不是逐页改颜色。

### 1. 身份层

包括站点名称、描述、关键词、头像、个人简介、首页标题和社交链接。

这一层要统一口径。首页写“技术博客”，关于页却介绍整套模板，搜索结果又会显得身份模糊。身份层完成后，后续文案才有稳定语气。

### 2. 信息架构层

导航只保留当前有真实内容的入口。留言板依赖评论服务，相册依赖真实照片，打赏依赖明确的收款方式；这些条件不满足时，隐藏入口比展示空页面更诚实。

归档、分类、标签和系列继续保留，因为它们直接服务于文章组织，而不是装饰。

### 3. 内容层

模板自带的演示文章适合展示能力，不适合长期占据首页。它们通常使用 1970 年作为示例日期，内容围绕 Markdown、图表和主题功能展开。

重整时应当：

1. 先备份原始内容。
2. 删除或归档模板演示。
3. 用真实栏目替换内容结构。
4. 至少准备一批可以互相链接的原创文章。
5. 让置顶文章说明站点当前阶段。

只删不加会让首页显得空，只加不删则会让默认内容和真内容混在一起。

### 4. 运营层

运营不是每天发一篇，而是让每次发布都可重复：

- 文章文件名规则
- Frontmatter 字段规范
- 图片命名与压缩
- 发布前检查
- 构建与部署路径
- 出现问题时如何回滚

这些流程可以写在仓库文档里，也可以在后续交给编码助手执行。规则越明确，临时修改越少。

## 这次实际替换了什么

当前整理围绕“能长期维护”展开：

- 站点描述改为网站运营、前端开发、内容方法与长期写作。
- 首页横幅和公告换成本站自己的文案。
- 移除示例友链、示例打赏者、模板音乐与测试相册。
- 关闭未配置评论服务的留言入口。
- 删除模板演示文章，新增围绕站点运营与 Firefly 实践的文章。
- 项目页改为介绍当前站点，而不是复制上游模板说明。
- GitHub Pages 构建读取 `BASE_PATH`，适配 `/Firefly/` 子路径。

这些改动不追求一次把所有模块做完，而是先把“现在能访问的内容都是真实内容”这件事做好。

## 判断是否真正脱离模板

可以用下面几个问题自检：

- 首页第一屏是否还出现上游项目的演示口号？
- 列表里是否还有 1970 年文章？
- 导航中是否有无法使用的入口？
- 关于页是否仍在介绍模板，而不是本站？
- 项目页、友链和动态是否存在明显示例数据？
- 仓库文档是否还能让下一次修改找到入口？

全部回答“否”之后，模板才真正变成了自己的站点。

模板提供结构和能力，站点身份、内容边界与运营规则必须由站长自己建立。完成这一步，后续每一次写作和开发才有稳定的落点。
